# 学習アプリ 要件定義書(MVP版)

## 1. 目的・背景

英語学習(将来的には他言語にも拡張可能)を対象に、ユーザーのレベルや学習実績に応じてAIが学習計画・学習コンテンツを提供するWeb/モバイルアプリを、一般向けプロダクトとして開発する。

本書はMVP(最小機能)の要件定義であり、まずリリース可能な最小構成を定義し、その後段階的に機能を拡張する前提で書かれている。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 学習計画 | ユーザーの目標・レベル・可処分時間をもとに生成される、期間ごとの学習内容の計画。アプリ内部ではJSON形式で保持 |
| 学習コンテンツ | 単語帳・文法問題・リスニング問題・スピーキング課題など、ユーザーが実際に学習する素材 |
| 学習実績 | ユーザーが学習コンテンツに取り組んだ結果(正誤・所要時間・実施日時等)の記録 |
| 忘却曲線 | エビングハウスの忘却曲線に基づく復習タイミングの管理(間隔反復: Spaced Repetition) |

## 3. アクター定義

| アクター | 説明 |
|---|---|
| エンドユーザー | アプリを使って学習する一般利用者 |
| システム管理者 | 学習コンテンツやユーザーアカウントを管理する運営者 |
| システム(AI/バッチ処理) | 学習計画生成・コンテンツ生成・忘却曲線管理などを自動で行う内部処理。人間のアクターではないが、機能要件上は「誰が何をするか」を明確にするため区別して記載 |

## 4. スコープ(MVP境界線)

要求いただいた機能を、MVPで実装する範囲と、MVP後(Phase 2以降)に回す範囲に仕分けた。

| # | 機能 | MVP | Phase 2以降 | 理由 |
|---|---|:---:|:---:|---|
| 1 | サインアップ / ログイン / ログアウト | ✅ | | 必須の基盤機能 |
| 2 | 学習計画をAIと相談してJSON出力 | ✅(簡易版) | 高度化 | 対話による計画生成はMVPでも中核機能だが、当初はシンプルなヒアリング→固定フォーマット生成に絞る |
| 3 | 学習実績を記録する機能 | ✅ | | 忘却曲線・コンテンツ推薦の前提データとして必須 |
| 4 | 学習する機能(コンテンツ消化) | ✅ | | コア体験 |
| 5 | 管理者: 学習コンテンツのデータメンテ | ✅(CRUD程度) | 高度化 | 最低限の管理画面は必要 |
| 6 | 管理者: ユーザーの参照・更新 | ✅ | | サポート対応・不正対応に必須 |
| 7 | 学習コンテンツ管理(システム機能) | ✅ | | 上記5と連動 |
| 8 | レベル・学習結果を元にした学習計画作成(AI) | △(簡易ルールベース) | 本格AI化 | MVPではAIによる対話生成 + 簡単な難易度調整に留め、精緻な最適化は次フェーズ |
| 9 | 学習結果から学習コンテンツを提供 | △(簡易な出題ロジック) | 高度化 | MVPは「間違えた分野を優先出題」程度のシンプルなロジック |
| 10 | 忘却曲線の管理・学習計画への反映 | ❌ | ✅ | 間隔反復アルゴリズム(SM-2等)の実装は難易度が高くMVP範囲外 |
| 11 | テストを生成する機能 | △(既存コンテンツからの出題) | AI動的生成 | MVPでは事前登録済み問題からの組み合わせ出題に留める |
| 12 | 単語帳を生成する機能 | △(既存コンテンツから抽出) | AI動的生成 | 同上 |
| 13 | 文法を学習させる機能 | ✅(コンテンツ表示のみ) | 個別最適化 | 教材の表示・進捗管理はMVP、個別最適な出し分けは次フェーズ |
| 14 | リスニング問題を作成する機能 | ❌ | ✅ | 音声生成・音源管理が必要でMVP範囲外。MVPでは事前登録済み音源を使用 |
| 15 | スピーキングを練習させる機能 | ❌ | ✅ | 音声認識・発音評価が必要で技術難易度が高くMVP範囲外 |

**MVPの一言サマリー**: 「事前に管理者が登録した学習コンテンツ(単語帳・文法・リスニング)を、AIとの簡単な対話で作った学習計画に沿って学習し、実績を記録する」ところまでをMVPとする。忘却曲線・コンテンツの動的自動生成・スピーキング練習は Phase 2以降。

## 6. 機能要件詳細(MVP)

### 6.1 認証(UC-01〜03)
- メールアドレス+パスワードでのサインアップ/ログイン(将来的にSNSログイン拡張余地を残す)
- ログアウト機能
- パスワードリセット機能(要検討: MVPに含めるか — 実運用上は必須級のため含めることを推奨)

### 6.2 学習計画作成(UC-04, UC-20)
- ユーザーが目標(例: 資格試験、面接対策等)・現在レベル・週あたりの学習可能時間をAIとの対話形式で入力
- AIが対話内容をもとに、期間・フェーズ・週次タスクを含む学習計画をJSON形式で生成
- 生成されたJSONはアプリ内のデータベースに保存され、学習画面・進捗画面に反映される
- JSONスキーマの設計が必要(後述データモデル参照)

### 6.3 学習実行(UC-05)
- 学習計画に基づき、その日/週に取り組むべきコンテンツをユーザーに提示
- コンテンツ種別: 単語帳、文法問題、リスニング問題(MVPでは事前登録音源のみ)
- 各コンテンツの解答・進捗を記録

### 6.4 学習実績記録(UC-06)
- 正誤、所要時間、実施日時を記録
- ユーザーが自分の実績を振り返れる画面(進捗率、正答率の推移等)

### 6.5 管理者機能(UC-10〜12)
- 学習コンテンツのCRUD画面(単語帳・文法・リスニング問題)
- ユーザー一覧・詳細参照、ステータス変更(利用停止等)

## 7. データモデル概要(主要エンティティ)

MVP時点で想定される主要エンティティ。詳細設計(カラム定義等)は別途基本設計フェーズで行う。

- **User**: ユーザーID、メールアドレス、パスワードハッシュ、レベル情報、作成日時 等
- **LearningPlan**: ユーザーID、目標、フェーズ構成(JSON)、生成日時、AIとの対話ログ(任意)
- **LearningContent**: コンテンツID、種別(単語/文法/リスニング)、難易度、本体データ、作成者(管理者)、作成日時
- **LearningRecord**: ユーザーID、コンテンツID、正誤、所要時間、実施日時
- **Admin**: 管理者ID、権限レベル

学習計画(LearningPlan)のJSON構造は、既存の「英語学習ロードマップ」(`english_roadmap.html`)で使ったフェーズ/週次タスク/マイルストーンの構造を参考にできる。

## 8. 非機能要件(MVP時点で考慮すべき項目)

| 項目 | MVPでの方針 |
|---|---|
| セキュリティ | パスワードのハッシュ化、通信のHTTPS化、個人情報(メールアドレス等)の適切な管理 |
| 可用性 | 一般公開前提のため、最低限のエラーハンドリングと落ちない設計は必須 |
| スケーラビリティ | Supabase / Node.jsベースで水平スケール可能な構成を意識(具体的な想定ユーザー数は要確認事項) |
| AI利用コスト | 学習計画生成(Claude/OpenAI)とリスニング音源生成(OpenAI TTS)は呼び出し・生成量に応じて課金が発生する。TTSは生成結果をキャッシュして再利用することでコストを抑制する方針 |
| 多言語対応 | MVPでは日本語UI + 英語学習のみを想定(学習対象言語の拡張はPhase 2以降) |

## 9. 決定事項(今回の相談で確定)

| 項目 | 決定内容 |
|---|---|
| 収益モデル | フリーミアム(ただしMVP時点では課金導線は実装せず無料版のみ提供。Phase 2で課金・広告を有効化) |
| AIバックエンド | Claude API と OpenAI(ChatGPT) API の両方を利用 |
| モバイル実装方式 | Expo(React Native)によるクロスプラットフォーム開発 |
| 認証・DB | Supabase |
| バックエンド | Node.js + TypeScript |
| 想定ユーザー規模 | ローンチ時点で約100名。ただしスケールアウト可能な設計を前提とする |
| リスニング音源 | ChatGPT(OpenAI)TTSで生成 |
| 決済手段 | App Store / Google Play のストア課金(アプリ内課金)。**MVPでは未実装、Phase 2で対応** |
| 広告収益 | Phase 2で導入 |
| Web版決済(クレジットカード) | Phase 2以降でさらに後回し(ストア課金・広告より後) |
| 無料プランの範囲 | AI学習計画生成は生涯1回のみ無料。それ以外はAIを使わない機能のみ提供 |

**MVPの位置づけの整理**: 決済がPhase 2に回ったため、MVPは実質「無料版のみを一般公開する」フェーズとなる。フリーミアムとしての差別化(有料プラン)はPhase 2の決済実装と同時に始まる。したがってMVPでは「無料ユーザーが不便すぎない範囲」で機能を絞ることが特に重要になる(9-1参照)。

### 9-1. 無料プランの範囲(MVP)

| 機能 | MVP無料プランでの扱い |
|---|---|
| サインアップ・ログイン・ログアウト | ✅ 提供 |
| 学習コンテンツへのアクセス(単語・文法・リスニング) | ✅ 提供(AIを使わない静的コンテンツのため無制限でも問題ない) |
| 学習実績の記録・閲覧 | ✅ 提供 |
| AI学習計画生成 | **生涯1回のみ**。2回目以降は「Phase 2で有料プラン提供予定」等の案内を表示するに留める(課金導線自体はまだ作らない) |
| 忘却曲線・AI動的コンテンツ生成・スピーキング練習 | Phase 2以降の機能のため、そもそもMVPには存在しない |

具体的な制限値(例: コンテンツ閲覧数に何らかの上限を設けるか等)は、システムコスト(特にOpenAI TTS・LLM APIの利用料)を見ながら運用開始後に調整する前提とし、MVP設計時点では「AI呼び出しを伴う機能=生涯1回」以外は原則無制限とする。

### 9-2. 残る要確認事項

1. **無料プランの具体的な追加制限値**: システムコスト(TTS生成量、LLM呼び出し量等)を実際に計測した上で、必要であれば静的コンテンツ側にも制限を設けるか判断する(運用しながら調整する前提でよいか確認)
2. **Phase 2の決済実装方式**: ストア課金(App Store/Google Play)をExpoでどう実装するか(react-native-iap、または決済管理を簡略化できるRevenueCat等の利用を検討)
3. **Phase 2の広告ネットワーク選定**: AdMob等、どの広告SDKを使うか

## 10. 技術スタック・アーキテクチャ概要

| レイヤー | 採用技術 | 役割 |
|---|---|---|
| フロントエンド | Expo(React Native)+ TypeScript | iOS/Android/Webを単一コードベースで開発(Expo for Web) |
| 認証・DB・ストレージ | Supabase(PostgreSQL, Auth, Storage, Realtime) | ユーザー認証、学習コンテンツ・実績・計画データの永続化 |
| バックエンド/API | Node.js + TypeScript | AI API呼び出しの仲介、将来の課金ロジック、Supabaseだけでは完結しないビジネスロジック |
| AI連携(テキスト) | Claude API / OpenAI API | 学習計画生成(対話)、将来的なコンテンツ動的生成 |
| AI連携(音声) | OpenAI TTS API | リスニングコンテンツ用の音声生成 |

**設計上の推奨ポイント**

- **AIプロバイダの抽象化層を設ける**: Claude APIとOpenAI APIの両方を使う想定なので、バックエンド側に「LLMアダプター」のような抽象化レイヤーを置き、機能ごと(学習計画生成・将来のテスト生成等)にどちらのAPIを使うか設定で切り替えられるようにしておくと、料金改定やモデル性能変化に強くなる
- **APIキーはクライアントに置かない**: Expoアプリ(クライアント)から直接Claude/OpenAI APIを呼ぶとAPIキーが漏洩するため、必ずNode.jsバックエンド経由で呼び出す構成にする
- **Supabase Row Level Security(RLS)の活用**: 一般公開プロダクトなので、ユーザーが他人の学習実績・学習計画にアクセスできないよう、Supabaseのテーブルごとに適切なRLSポリシーを設定する
- **Supabase Edge Functions の活用検討**: 軽量なAPI呼び出し中継であれば、別途Node.jsサーバーを立てず、Supabase Edge Functions(Deno製サーバーレス関数)で代替できる可能性がある。運用コスト・複雑さを抑えたい場合はこちらも検討候補
- **リスニング音源はTTS生成結果をキャッシュする**: OpenAI TTSは呼び出しごとに課金が発生するため、管理者がリスニングコンテンツを登録した際に一度だけTTS生成してSupabase Storageに音声ファイルを保存し、以降はユーザーからのリクエスト時にキャッシュ済み音源を返す設計にすると、コストを大きく抑えられる(毎回動的生成しない)
- **想定100名規模でもスケールアウトを見据えた設計**: 初期規模は小さいが将来のスケールを見据え、(1)Node.jsバックエンドをステートレスに保ちインスタンスを水平に増やせる構成にする、(2)Supabaseは規模に応じてプランをアップグレード可能、(3)AI API呼び出しはキュー(ジョブ)化しておくと同時アクセス増加時にも耐えやすい、といった点を初期設計段階から意識しておくと後々の作り直しを避けられる

## 11. 今後のロードマップ(Phase 2以降・参考)

- **Phase 2**:
  - 忘却曲線(間隔反復)による復習管理
  - AIによるテスト・単語帳・リスニング問題の動的生成
  - ストア課金の実装(App Store / Google Play のアプリ内課金。react-native-iapまたはRevenueCat等を利用)
  - 広告による収益化(AdMob等の広告SDK導入)
- **Phase 3**: スピーキング練習(音声認識・発音評価)、学習計画の高度な個別最適化
- **Phase 4以降**: Web版のクレジットカード決済(Stripe等)対応、多言語学習対応、SNS/コミュニティ機能等の検討(要相談)
