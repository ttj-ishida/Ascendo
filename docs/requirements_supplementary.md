# 学習アプリ 要件定義 補足資料

`requirements_mvp.md` を補足する資料。前提条件・制約条件・リスク・成功指標(KPI)・画面一覧をまとめる。

---

## 1. 前提条件(Assumptions)

要件定義・設計の前提として置いている事項。実態と異なる場合は要修正。

- 主な利用者は日本語話者で、英語学習を主目的とする(UIは日本語、学習対象言語は英語)
- ユーザーはスマートフォン(iOS/Android)またはWebブラウザからアクセスし、常時インターネット接続がある環境を前提とする(オフライン学習は非対応)
- MVP時点では決済機能を持たないため、運用初期の収益はゼロという前提でインフラ・AI利用コストを見積もる
- 管理者(システム管理者)は運営チーム内の少人数(1〜数名)を想定し、大規模な権限管理(ロール細分化等)は不要

## 2. 制約条件(Constraints)

- **外部API利用規約への準拠**: Claude API、OpenAI API(TTS含む)の利用規約・レートリミット・コンテンツポリシーに従う必要がある
- **ストア審査ガイドライン**: Phase 2でApp Store/Google Playの課金・広告機能を実装する際は、各ストアの審査ガイドライン(特にサブスクリプション表示要件、広告掲載基準)に準拠する必要がある
- **個人情報保護**: ユーザーのメールアドレス・学習履歴等を扱うため、個人情報保護法(および将来海外展開する場合はGDPR等)への対応を考慮する
- **予算・体制**: 具体的な開発予算・人員体制は本書の対象外(別途確認が必要な場合は追記)

## 3. リスクと対応方針

| リスク | 影響 | 対応方針 |
|---|---|---|
| AI API利用コストがユーザー数増加時に想定以上に膨らむ | 収益化前のMVP期間中の運用コスト超過 | 学習計画生成を無料プランで生涯1回に制限、TTS音源はキャッシュして再利用、利用状況をモニタリングし早期にアラートを出す仕組みを用意 |
| ストア審査(Phase 2の課金・広告)によるリリース遅延 | Phase 2のリリーススケジュール遅延 | 審査ガイドラインを事前に確認し、余裕を持ったスケジュールを組む。RevenueCat等、審査対応の実績があるSDKの利用を検討 |
| 忘却曲線アルゴリズム(Phase 2)の精度が低く学習効果を感じられない | ユーザー離脱・低評価レビュー | MVP期間中にユーザーの学習実績データを蓄積し、Phase 2実装前にアルゴリズムの妥当性を検証する |
| 個人情報・学習データの漏洩 | 信頼失墜、法的リスク | Supabase RLSの徹底、通信のHTTPS化、最小権限の原則でのアクセス制御 |
| 無料ユーザーの体験が乏しく定着しない(AI利用が生涯1回のみのため) | 有料転換前にユーザーが離脱してしまう | 静的コンテンツ(単語・文法・リスニング)を無料で十分に使えるようにし、AI機能なしでも学習継続できる設計にする(すでに要件に反映済み) |
| Claude API / OpenAI APIの仕様変更・値上げ | 機能停止やコスト増 | LLMアダプター層による抽象化で、プロバイダ切り替えを容易にしておく(すでに要件に反映済み) |

## 4. 成功指標(KPI)候補

事業的な成功をどう測るかの叩き台。**具体的な目標値は事業計画側で別途確定が必要**。

| フェーズ | 指標候補 |
|---|---|
| MVP(無料版のみ) | サインアップ数、学習計画生成→初回学習実施までの転換率、7日後継続率(D7 Retention)、平均週次学習時間 |
| Phase 2(課金・広告導入後) | 無料→有料転換率、月間経常収益(MRR)、広告収益(eCPM等)、有料プラン継続率(チャーン率) |
| 全期間共通 | アプリストア評価スコア、サポート問い合わせ件数(品質の間接指標) |

## 6. 開発スケジュールの概要(参考・要調整)

具体的な日程は体制・予算に応じて別途決めるべきだが、フェーズの前後関係の参考として記載する。

1. **要件定義**(本書 + `requirements_mvp.md`) ← 現在ここ
2. **基本設計**: データモデル詳細(テーブル定義)、学習計画JSONスキーマ設計、画面遷移設計、API設計
3. **MVP開発**: 認証、学習コンテンツ管理、AI学習計画生成(簡易版)、学習実行・実績記録
4. **MVPリリース・運用**: 実際の利用状況・コストを計測しながら運用
5. **Phase 2開発**: 忘却曲線、AI動的コンテンツ生成、ストア課金、広告
